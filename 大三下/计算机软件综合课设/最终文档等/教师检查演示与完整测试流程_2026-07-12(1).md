# 实验室预约与设备管理系统：最终检查演示与完整测试流程

**适用版本：** 2026-07-16 最终完整功能版  
**最后更新：** 2026-07-16  
**线上入口：** `https://example.com/app`  
**健康检查：** `https://example.com/health`  
**建议演示时长：** 主线 25～30 分钟；含所有扩展项 45～60 分钟

## 1. 演示目标

这套流程用于向老师证明：

1. 系统是真正部署在服务器上的在线软件，可由不同电脑同时访问。
2. 平台、预约、场地设备、信用运营四个模块共享统一 Flask 入口、Session 身份和 SQLite 数据库。
3. 学生、实验室管理员和系统管理员具有不同菜单、接口权限和实验室数据范围。
4. FR-01～FR-13 已形成资源查询、预约审批、现场使用、信用、运维、通知、统计和审计闭环。
5. 公网入口使用受信任 HTTPS，可调用浏览器真实定位；登录 Cookie 使用安全属性。
6. 所有演示操作可通过一键重置恢复到确定状态。

## 2. 演示设备与账户

### 2.1 推荐窗口安排

最好使用三台电脑，或同一台电脑的三个互不共享 Cookie 的浏览器会话：

| 窗口 | 账户 | 主要用途 |
| --- | --- | --- |
| 学生端 S | `student / <STUDENT_DEMO_PASSWORD>` | 查询资源、预约、定位签到、报修、信用恢复、通知 |
| 实验室管理端 M | `labadmin / <LAB_ADMIN_DEMO_PASSWORD>` | 审批、人工核验、维修、违规、恢复审核、统计 |
| 系统管理端 A | `admin / <SYSTEM_ADMIN_DEMO_PASSWORD>` | 用户、角色、实验室、参数、备份和日志 |
| 封禁验证端 B | `assistant / <ASSISTANT_DEMO_PASSWORD>` | 多角色切换和低信用预约拦截，可复用学生端 |

不要在同一浏览器普通窗口的多个标签页中登录不同账户，因为标签页会共享 Session。可使用 Chrome、Edge、Firefox、无痕窗口或独立浏览器配置文件。

### 2.2 演示前准备

1. 浏览器缩放设为 100%，关闭自动翻译和会遮挡页面的悬浮工具。
2. 三个窗口都打开 `https://example.com/app`，确认地址栏没有证书警告。
3. 学生端第一次使用定位时，在浏览器权限弹窗中选择“允许”。
4. 准备报修和信用恢复附件，可直接使用：  
   `D:\softwareproject\图\全系统模块与部署架构图_2026-07-12.drawio.png`
5. 准备用户批量导入文件：  
   `D:\softwareproject\交接\演示用户批量导入.csv`
6. 保留一个 PowerShell 窗口，用于数据重置和健康检查。

## 3. 一键准备演示数据

### 3.1 执行时机

在正式演示开始前 0～5 分钟执行。预约 `#7` 在重置后 10 分钟开始，用于无迟到的人工核验；预约 `#1` 从重置时刻前 5 分钟开始并持续约 2 小时；预约 `#2` 从重置时刻后 2 小时开始。因此重置后应先演示第 4.2 节人工核验，再继续其他主线。

### 3.2 一键重置

在 Windows PowerShell 中执行：

```powershell
ssh root@example.com "lab-system-demo-reset"
```

输入服务器 SSH 密码。该命令会：

1. 停止 `lab-system`，避免重置时并发写入。
2. 备份当前数据库到 `/var/lib/lab-system/demo-backups/`。
3. 清理预约、签到、报修、违规、信用恢复、通知、日志和上传附件等演示数据。
4. 恢复 2 个实验室、3 台设备及每天 `08:00～22:00` 的开放规则。
5. 恢复四个演示账户、密码、角色、管辖范围和系统参数。
6. 写入 7 条固定预约，并设置 student 为 100 分、assistant 为 55 分且封禁 7 天。
7. 重启服务并执行四模块健康检查。

命令末尾应出现：

```json
{"modules":["platform","reservation","field-equipment","credit-operations"],"service":"lab-system","status":"ok"}
```

### 3.3 记录动态日期和编号

```powershell
ssh root@example.com "cat /var/lib/lab-system/demo-state.md"
```

把“日程演示日期”记为 **D 日**。重置后固定预约如下：

| 编号 | 设备 | 初始状态 | 演示用途 |
| --- | --- | --- | --- |
| `#1` | 高性能工作站 A02 | approved | 当前时间段定位签到、迟到违规、签退和报修 |
| `#2` | GPU 训练节点 B01 | approved | 临期取消与自动扣分 |
| `#3` | 高性能工作站 A01 | pending | D 日 `09:00～10:00` 待审批占用 |
| `#4` | 高性能工作站 A01 | approved | D 日 `10:30～12:00` 已占用时段 |
| `#5` | 高性能工作站 A01 | approved | 昨日未签到，供定时扫描扩展演示 |
| `#6` | GPU 训练节点 B01 | completed | 历史完成记录 |
| `#7` | 高性能工作站 A01 | approved | 重置后 10 分钟开始，专门演示定位失败与人工补签 |

### 3.4 公网健康检查

```powershell
Invoke-RestMethod https://example.com/health
```

确认 `status=ok`，且 `modules` 有四项。旧的 HTTP 地址会自动跳转到 HTTPS，但演示时应始终使用 HTTPS 地址。

## 4. 主线演示流程

### 4.1 HTTPS 登录、统一身份和角色隔离（FR-01）

**学生端 S：**

1. 输入 `student / <STUDENT_DEMO_PASSWORD>` 并登录。
2. 右上角应显示“学生用户 · 学生”。
3. 总览应显示 7 条初始预约、3 台正常设备、信用分 100 和至少 1 条未读通知。
4. 左侧应有预约、实验室与设备、现场使用与报修、信用与通知；不应有系统管理和统计分析。

**实验室管理端 M：**

1. 输入 `labadmin / <LAB_ADMIN_DEMO_PASSWORD>` 并登录。
2. 总览显示待审批、待处理报修、人工核验和未读通知四类待办。
3. 可以看到统计分析和管辖范围内的资源管理，不显示学生个人信用分。

**系统管理端 A：**

1. 输入 `admin / <SYSTEM_ADMIN_DEMO_PASSWORD>` 并登录。
2. 只保留总览、实验室与设备、统计分析、系统管理等管理入口。
3. 不显示个人预约、签到、报修和信用运营入口。

**讲解口径：** 菜单隔离只是第一层；接口还依据服务器 Session、角色权限和 `admin_lab_scope` 再次校验，客户端不能通过伪造用户编号或角色获得权限。

### 4.2 独立人工核验与补签（FR-06）

本节应在重置后 10 分钟内优先完成，使用专用预约 `#7`，不会占用真实定位预约 `#1`。

**学生端 S：**

1. 打开“现场使用与报修”。
2. 签到预约编号填 `7`，点击“模拟扫码”。
3. 不点击“浏览器定位”，直接点击“申请人工核验”。
4. 说明填 `浏览器定位超时，请现场核验身份`。
5. 页面提示人工核验申请已提交；预约仍为 approved，不会在学生端自行完成签到。

**实验室管理端 M：**

1. 打开“现场使用与报修”，刷新“人工签到核验”。
2. 找到预约 `#7` 的申请，点击“通过并补签”。
3. 意见填 `现场身份与预约信息一致`，二次确认。
4. 预约 `#7` 变为 using，签到记录的验证方式为 manual，核验人是当前管理员。

**学生端 S：**

1. 在签退区域输入 `7`，点击“确认签退”。
2. 预约 `#7` 变为 completed。

**讲解口径：** 定位失败不会让学生绕过服务端校验。学生只能提交本人已通过预约的申请，管辖管理员审核通过后才由服务端补签；申请、审核意见、核验人、签到和 IoT 日志都有记录。

### 4.3 资源组合查询（FR-02）

**学生端 S：**

1. 打开“实验室与设备”。
2. 实验室选“软件工程实验室”。
3. 设备类型填 `工作站`。
4. 日期选择 D 日，开始时刻 `12:00`，结束时刻 `13:00`。
5. 状态选“正常”，关键词可填 `A0`，点击“查询”。
6. 应显示符合条件的工作站及其可预约时段。
7. 把结束时刻改为 `23:00` 再查询，应显示没有满足该时间段的资源，因为开放时间到 `22:00`。

**讲解口径：** 查询同时支持实验室、类型、日期、时段、状态和关键词；结果不是静态设备表，而是结合开放规则、维修状态和预约占用实时计算。

### 4.4 查看设备日程并提交预约（FR-03）

**学生端 S：**

1. 打开“预约管理”。
2. 选择“软件工程实验室”和“高性能工作站 A01”。
3. 开始时间填 D 日 `13:00`，结束时间填 D 日 `14:00`。
4. 设备日程应自动显示：
   - 开放时段 `08:00～22:00`；
   - 已占用 `09:00～10:00`、`10:30～12:00`；
   - 可预约 `08:00～09:00`、`10:00～10:30`、`12:00～22:00`。
5. 日程不应显示其他预约人的姓名、用途或预约编号。
6. 用途填 `课程设计演示：多人在线预约`，点击“提交预约”。
7. 页面提示“预约已提交，已通知实验室管理员”。
8. “我的预约”新增一条 pending 记录，通常为 `#8`，下文记为 **R8**。

**讲解口径：** 前端幂等键优先使用 `crypto.randomUUID()`，不支持时自动退回时间戳随机串；服务端仍执行资格、资源状态和事务内冲突检查。

### 4.5 管理员审批、意见、二次确认与通知（FR-04、FR-12）

**实验室管理端 M：**

1. 打开“预约管理”，在“待审批预约”选择软件工程实验室并查询。
2. 应看到预置 `#3` 和刚提交的 R8，并能看到申请学生当前信用分。
3. 找到用途“课程设计演示：多人在线预约”，点击“通过”。
4. 审批意见填写 `资源与信用均符合要求`。
5. 在“确认通过该预约？”对话框选择确认。
6. 页面提示预约已通过，该记录从待审批列表消失。

**学生端 S：**

1. 点击“我的预约”区域的“刷新”，R8 应变为 approved。
2. 打开“信用与通知”，应出现“预约已通过”通知，并包含审批意见。
3. 点击该通知的“标记已读”，状态由 unread 变为 read。

**讲解口径：** 提交和审批都会通知相关人员并写审计日志；审批前再次复核冲突和设备状态，防止提交后资源发生变化。

### 4.6 冲突、替代设备和异常日志（FR-03、FR-13）

**学生端 S：**

1. 仍选择 A01 和 D 日 `13:00～14:00`。
2. 用途填 `冲突预约验证`，再次提交。
3. 系统应返回冲突提示，不新增有效预约。
4. 页面保留冲突设备日程；若存在同类型可用设备，还会提示同类设备建议。

**系统管理端 A：**

1. 稍后进入“系统管理”的“异常日志”。
2. 应能看到这次 `POST /api/reservations` 的 `409` 业务冲突记录。

**讲解口径：** 409 不代表服务器崩溃，而是可预期业务异常；系统记录接口、用户、状态码和信息，方便排查。B 模块的短写事务和唯一幂等约束保证并发预约不会双重成功。

### 4.7 HTTPS 真实定位签到与 IoT 模拟（FR-06）

本节使用预约 `#1`，应在重置后约 90 分钟内完成。

**学生端 S：**

1. 打开“现场使用与报修”。
2. 签到预约编号填 `1`。
3. 点击“模拟扫码”，动态二维码令牌自动填入。
4. 点击“浏览器定位”。
5. 首次弹出权限请求时选择“允许”。
6. 页面应提示定位成功并显示约多少米精度；“定位验证通过”自动勾选。
7. 点击“确认签到”，页面提示“签到成功”。

**实验室管理端 M：**

1. 打开“现场使用与报修”，刷新“IoT 指令日志”。
2. 应看到与预约 `#1` 对应的开锁和设备上电模拟指令。

签到成功后，预约从 approved 变为 using。由于预约开始时间是重置前 5 分钟，系统还会产生一条 `late_check_in` 待确认违规。

> 若演示电脑无法取得真实定位，不要手动勾选定位复选框。预约 `#7` 已经证明人工核验闭环；预约 `#1` 可以保留为“真实定位失败时服务端拒绝签到”的异常展示。

### 4.8 签退和违规确认（FR-06、FR-09）

**学生端 S：**

1. 签退预约编号填 `1`，点击“确认签退”。
2. 页面提示签退成功，预约状态变为 completed。

**实验室管理端 M：**

1. 刷新 IoT 日志，应新增设备下电记录。
2. 打开“信用与通知”，刷新违规列表。
3. 找到 `late_check_in`、pending 记录，点击“确认扣分”。
4. 扣分值保持 `5`，核实意见填 `签到时间超过允许范围`，二次确认。

**学生端 S：**

1. 刷新“信用与通知”。
2. 信用分应从 100 变为 95。
3. 信用变动明细和通知中心都应出现本次扣分。

**讲解口径：** C 模块产生带现场证据的疑似违规，D 模块负责管理员确认、扣分和封禁，整合层负责身份、范围、通知和 A 模块审计。

### 4.9 临期取消和自动扣分（FR-05、FR-09）

**学生端 S：**

1. 打开“预约管理”，找到 `#2`“演示：临期取消自动扣分”。
2. 点击“取消”。
3. 页面提示预约已进入临期时段，选择继续。
4. 预约状态变为 cancelled。
5. 回到“信用与通知”刷新，信用分应从 95 变为 90。

若跳过上一节违规确认，则应从 100 变为 95。

**讲解口径：** `cancel_exemption_hours=2` 和 `late_cancel_deduction=5` 来自可版本化系统参数；学生主动临期取消会扣分，管理员因维修取消则不会扣学生信用。

### 4.10 附件报修和维修闭环（FR-07、FR-12）

预约 `#1` 完成后，student 与高性能工作站 A02 建立了近期使用关系。

**学生端 S：**

1. 打开“现场使用与报修”。
2. 设备选“高性能工作站 A02”。
3. 故障类型填 `显示异常`。
4. 情况描述填 `演示中发现显示器间歇性闪烁`。
5. 现场图片选择预先准备的 PNG 文件。
6. 点击“提交报修”。
7. 报修记录出现附件“查看”链接，状态为 pending，设备状态变为 fault_pending。

**实验室管理端 M：**

1. 总览的待处理报修数量和通知应变化。
2. 打开“现场使用与报修”并刷新报修记录。
3. 点击“查看”确认附件可访问。
4. 点击“开始维修”，处理结果填 `已受理并开始维修`，确认提交。
5. 状态变为 repairing，设备状态同步变为 repairing。
6. 点击“完成维修”，处理结果填 `维修完成，设备恢复正常`。
7. 报修状态变为 completed，设备恢复 normal。

**替代分支：** pending 状态可选择“确认无故障”；若核实为人为损坏，可使用“关联人为损坏”并填写责任学生和证据，由系统创建相应疑似违规。

### 4.11 信用恢复申请和范围审核（FR-10）

**学生端 S：**

1. 打开“信用与通知”。
2. 在“申请信用恢复”选择“申诉恢复”。
3. 关联扣分选择刚才的迟到或临期取消记录。
4. 申请分值填 `5`。
5. 原因填 `已核对现场情况并完成实验室规范学习`。
6. 证明材料选择准备好的 PNG 或 PDF，点击“提交申请”。
7. “信用恢复记录”新增 pending 记录。

**实验室管理端 M：**

1. 刷新“信用与通知”，找到该恢复申请。
2. 点击“通过”，审核意见填 `材料有效，同意恢复`。
3. 恢复分值保持 `5`，二次确认。

**学生端 S：**

1. 刷新后申请状态变为 approved。
2. 信用分增加 5 分，并收到恢复结果通知。

**讲解口径：** 申诉必须关联扣分记录，培训恢复可不关联；附件、申请、审核人、审核意见和恢复流水均留痕，实验室管理员只能审核管辖范围内学生的申请。

### 4.12 低信用封禁阻止预约（FR-09）

**封禁验证端 B：**

1. 使用 `assistant / <ASSISTANT_DEMO_PASSWORD>` 登录，当前角色保持“学生”。
2. 打开“信用与通知”，应看到信用分 55、预约资格“暂停预约”和有效封禁期限。
3. 打开“预约管理”，任选空闲设备和 D 日 `15:00～16:00`。
4. 用途填 `低信用预约拦截测试` 并提交。
5. 服务端应拒绝请求，不产生新预约。

**讲解口径：** B 模块在创建预约前实时调用 D 的预约资格判断，浏览器不会提交“信用合格”这种可伪造字段。

### 4.13 设备状态变更、影响预览和维护取消（FR-05、FR-08）

本节安排在 R8 已通过之后，演示完应恢复设备状态。

**实验室管理端 M：**

1. 打开“实验室与设备”，查询软件工程实验室的 A01。
2. 把设备状态从“正常”改为“维修中”，点击保存。
3. 系统应提示存在受影响预约并显示数量，不会直接保存。
4. 确认变更并取消受影响预约。
5. 设备变为 repairing，R8 及其他受影响的 pending/approved 预约变为 cancelled。

## 7. 常见问题与处理

| 现象 | 原因 | 处理方法 |
| --- | --- | --- |
| HTTPS 页面打不开 | Nginx、443 防火墙或证书异常 | 先访问 `/health`，再 SSH 检查 `nginx`、`lab-system`、Certbot timer |
| 浏览器显示证书警告 | 使用了旧缓存、代理改写或证书未更新 | 确认地址是 `https://example.com`，换浏览器测试，不要绕过警告继续演示 |
| 定位按钮失败 | 未授权、设备无定位能力或系统位置服务关闭 | 开启权限后重试；人工核验闭环可独立使用预约 `#7` 展示 |
| 预约 `#1` 无法签到 | 距重置时间过久或已被处理 | 重新执行一键重置 |
| 预约 `#7` 无法人工补签 | 已超过结束时间、尚未进入提前窗口或已处理 | 演示开始前 0～5 分钟重置，并优先执行第 4.2 节 |
| 预约 `#2` 无法取消 | 已超过开始时间 | 重新重置，并在 2 小时内演示 |
| D 日不一致 | 演示当天重新生成了相对日期 | 以 `demo-state.md` 为准 |
| R8 不是 `#8` | 重复操作导致编号递增 | 按用途查找，以页面实际编号为准 |
| 报修被拒绝 | 尚未完成预约 `#1`，没有设备使用关系 | 先完成签到和签退 |
| 看不到审批/报修/恢复申请 | 页面未刷新、角色错误或实验室不在范围 | 检查右上角角色并刷新对应列表 |
| 两个窗口互相被登出 | 两窗口共享 Cookie | 换用独立浏览器或无痕窗口 |
| 用户导入提示已存在 | 尚未重置或已经导入过样例 | 执行一键重置，或更换样例账号 |
| `crypto.randomUUID is not a function` | 浏览器缓存了旧版 JS | `Ctrl+F5` 强制刷新或清除该站点缓存 |

服务器检查命令：

```bash
systemctl status lab-system nginx snap.certbot.renew.timer
journalctl -u lab-system -n 100 --no-pager
curl -fsS http://127.0.0.1:8000/health
curl -fsS https://example.com/health
nginx -t
```

## 8. 恢复到演示前状态

### 8.1 推荐方式：再次一键重置

```powershell
ssh root@example.com "lab-system-demo-reset"
```

每次重置都会先生成数据库备份。重置完成后刷新或关闭所有演示窗口，避免页面仍显示重置前数据。

### 8.2 恢复某次重置前的数据库

先查看备份：

```powershell
ssh root@example.com "ls -lh /var/lib/lab-system/demo-backups/"
```

确认文件名后执行：

```powershell
ssh root@example.com "systemctl stop lab-system && cp /var/lib/lab-system/demo-backups/before-demo-reset-YYYYMMDD-HHMMSS.db /var/lib/lab-system/reservations.db && chown labapp:labapp /var/lib/lab-system/reservations.db && chmod 640 /var/lib/lab-system/reservations.db && systemctl start lab-system"
```

然后检查：

```powershell
Invoke-RestMethod https://example.com/health
```

不要在服务运行时直接覆盖 SQLite 数据库。

## 10. 开场与收尾口径

### 开场

> 本系统是部署在云服务器上的 HTTPS 在线软件。四个成员模块保留各自业务实现，通过统一 Flask 入口、服务器 Session、共享数据库和适配器协作。下面使用学生、实验室管理员和系统管理员三个会话，演示从资源查询、预约审批、现场使用、信用联动到运维、统计和审计的完整闭环。

### 收尾

> 本次演示覆盖了 FR-01 到 FR-13 的正常流程、冲突流程、权限异常和信用异常。关键判断都在服务器执行，跨模块操作具备幂等、通知和审计记录；当前单 Gunicorn worker 加 SQLite 满足课程规模，扩大并发时可迁移至 PostgreSQL、多 worker 和独立任务队列。
