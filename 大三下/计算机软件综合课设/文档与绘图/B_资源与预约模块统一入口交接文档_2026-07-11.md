## 1. 当前结论

B 模块已按 A 的统一 Flask 主入口交接文档完成本地代码调整。

当前 B 模块仍支持两种运行方式：

1. 独立运行：`b_reservation.create_app(config)`。
2. 接入统一入口：`b_reservation.register_routes(app, reservation_store, register_health=False)`。

统一入口接入方式与组长提供的 `unified_app.py` 保持一致：

```python
from b_reservation import ReservationStore, register_routes

reservation_store = ReservationStore(database_path)
reservation_store.init_schema()
register_routes(app, reservation_store, register_health=False)
```

接入统一入口时，B 不单独注册 `/health`，由全组统一入口返回总健康检查结果。

## 3. B 当前提供的 HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/health` | B 独立运行时健康检查；接入统一入口时不注册 |
| `POST` | `/api/reservations` | 学生提交预约，必须带 `Idempotency-Key` |
| `GET` | `/api/reservations/me` | 当前学生查看本人预约 |
| `GET` | `/api/labs/<lab_id>/reservations/pending` | 实验室管理员查看待审批预约 |
| `POST` | `/api/reservations/<id>/approve` | 实验室管理员审批通过 |
| `POST` | `/api/reservations/<id>/reject` | 实验室管理员驳回 |
| `POST` | `/api/reservations/<id>/cancel` | 学生取消预约，或管理员维护取消 |

## 4. B 依赖 A/C/D 注入的服务端能力

B 不信任前端传来的身份、权限、信用和设备状态字段，只从统一主入口注入的服务端回调获取结论。

| 回调 | 提供方 | B 的用途 |
|---|---|---|
| `CURRENT_ACTOR()` | A | 获取当前登录用户和当前角色 |
| `CAN_MANAGE_LAB(user_id, lab_id)` | A | 判断管理员是否有权审批该实验室预约 |
| `GET_PARAMETER(key, default)` | A | 后续读取取消免责时限、预约规则等系统参数 |
| `AUDIT(...)` | A | 创建、审批、驳回、取消预约时写操作日志 |
| `RESOURCE_IS_BOOKABLE(lab_id, equipment_id, start_time, end_time)` | C | 判断实验室/设备在目标时段是否可预约 |
| `STUDENT_IS_ELIGIBLE(user_id)` | D | 判断学生信用/封禁状态是否允许预约 |

D 未接入前，统一入口可以临时提供 `STUDENT_IS_ELIGIBLE` 适配函数；B 不在本模块内直接维护信用和封禁规则。

## 5. B 提供给 C 的预约联动能力

C 的签到签退、设备报修和维护流程可以调用 B 的 `ReservationStore` 方法。

| 方法 | 说明 |
|---|---|
| `get(reservation_id)` | 读取预约详情和当前状态 |
| `mark_using(reservation_id, now=None)` | C 签到核验通过后，把预约从 `approved` 改为 `using` |
| `mark_completed(reservation_id, now=None)` | C 签退核验通过后，把预约从 `using` 改为 `completed` |
| `list_affected_by_equipment(equipment_id, now=...)` | 设备报修/维护时查询受影响预约 |
| `cancel_for_maintenance(reservation_id, now=None)` | 设备维护导致取消预约，不触发学生临期取消扣分 |
| `student_has_equipment_relation(user_id, equipment_id, now=..., recent_days=...)` | C 报修时判断学生近期是否和设备存在预约使用关系 |

## 6. 数据库表

B 当前维护 `reservation` 表。

核心字段包括：

```text
reservation_id, request_id, user_id, lab_id, equipment_id,
start_time, end_time, purpose, status,
approver_id, approved_at, approve_comment, created_at
```

关键规则：

1. `request_id` 唯一，对应 HTTP `Idempotency-Key`，避免重复提交生成多条预约。
2. 预约时间按半开区间 `[start_time, end_time)` 判断冲突，首尾相接允许预约。
3. 有效冲突状态为 `pending`、`approved`、`using`。
4. SQLite 写入使用短事务和 `BEGIN IMMEDIATE`，保证冲突检查与写入在同一个事务内完成。
5. 临期取消只返回 `credit_deduction_required=True`，不直接写 D 的信用表。

## 9. 给组长集成时的注意点

1. 线上统一入口优先使用 `register_routes(app, reservation_store, register_health=False)`，不要再让 B 独立创建第二个 Flask app。
2. B 的 `DATABASE_PATH` 应与 A/C/D 共用同一个 SQLite 数据库文件。
3. 如果线上已有 C 模块，B 的 `mark_using`、`mark_completed`、`list_affected_by_equipment` 等方法可以直接暴露给 C。
4. D 未接入前，`STUDENT_IS_ELIGIBLE` 可由 A 临时适配；D 接入后再替换成真实信用/封禁判断。
5. 关键操作建议统一接 A 的 `AUDIT`，便于后续项目开发记录表、测试记录和老师检查。
