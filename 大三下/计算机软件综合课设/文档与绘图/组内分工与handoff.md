# 智能实验室预约与设备管理系统组内分工与 Handoff

> 本文档用于组内任务认领、阶段交接和减少重复劳动。分工不写姓名，四位组员可自行认领“角色 A/B/C/D”。  
> 原则：每个角色对自己负责的产物承担最终人工审查责任，包括文字核对、图表调整、代码审查、测试验证和答辩解释。AI 可作为效率工具，但提交产物必须经过人工判断、修改和一致性检查。

## 一、总体协作原则

### 1. 关键里程碑

| 日期 | 检查内容 | 组内目标 |
|---|---|---|
| 2026.7.6 | 《需求规格说明书》 | 完成全文人工校对、图片人工调整、术语/状态/数据库一致性检查 |
| 2026.7.13 | 《概要设计说明书》《详细设计说明书》、软件原型 | 完成设计文档定稿、原型可演示、核心流程图和界面图统一 |
| 2026.7.17 | 软件完全体、全部文档 | 完成系统演示、测试材料、用户手册、开发计划、开发记录、最终归档 |

### 2. 统一源文件规则

| 类型 | 统一源 | 规则 |
|---|---|---|
| 需求文档 | `230710_8_需求规格说明书_源稿.md` 和最终 `.docx` | 文档文字以源稿为准，Word 用于提交和排版 |
| 图表 | `图/` 文件夹下 `.drawio` | 所有文档共用同一张图时，只允许在统一源图上调整，不重复画第二版 |
| 旧版 DFD/状态图 | `软件课设第一次需求报告图/` | 若正式报告还引用，需同步到 `图/` 目录，避免两个版本冲突 |
| 软件代码 | 后续项目源码目录 | 每个模块提交前要说明接口、数据表依赖、测试方法 |
| 交接记录 | 本 handoff 文档或群公告 | 每次交接必须写“已完成、未完成、风险、下一步” |

### 3. 反重复劳动规则

1. 图表由“角色 B”统一维护。其他角色发现图有问题，只提修改意见，不自行另画同名图。
2. 数据库字段、状态枚举、权限模型由“角色 C”统一维护。其他角色引用时必须以 C 的最新版为准。
3. 软件代码由“角色 D”主导集成。其他角色如果写原型或小模块，必须先说明接口，避免重复实现。
4. 文档最终格式、目录、编号和提交包由“角色 A”统一整合。
5. 每个阶段结束前至少做一次全员 20 分钟同步，确认图、表、文档、代码没有互相矛盾。

### 4. 工作量平衡原则

为了避免 B、A 工作量明显偏轻，同时又不破坏代码和设计的连续性，采用“主责不拆散、人工重活再分配”的方式平衡：

1. D 仍然主导代码主线，不把核心代码切成多人拼接，减少集成风险。
2. B 不只负责画图，还负责原型验收、界面一致性、用户手册截图、演示脚本和黑盒测试用例设计。
3. A 不只负责排版，还负责最终质量门禁、交付包核查、文档之间的追溯矩阵和答辩材料整理。
4. C 负责设计正确性和数据一致性，但不独自承担所有后期核对，B 负责界面/流程核对，A 负责文档/提交核对。

## 三、角色 A Handoff：文档质量与提交负责人

### A.1 角色定位

角色 A 是“文档总编辑 + 提交流程负责人 + 最终质量门禁”。核心目标不是单纯写很多字，而是保证所有提交材料看起来来自同一个项目、同一套术语、同一套规则，并且能在答辩中解释清楚。

### A.2 负责范围

| 阶段 | 任务 |
|---|---|
| 第一阶段 | 人工校对《需求规格说明书》；检查图表编号、图片清晰度、文字风格；整理 7.6 检查版 |
| 第一阶段 | 与 B 确认所有图片是否统一；与 C 确认数据库、状态、角色权限描述是否一致 |
| 第二阶段 | 撰写并整合《项目开发计划书》 |
| 第二阶段 | 维护《项目开发记录表》，记录真实的人工审查、修改、实现、测试和会议活动 |
| 第二阶段 | 制作需求-设计-实现-测试追溯检查表，核对 FR 编号是否都有对应设计和测试 |
| 第二阶段 | 整理答辩材料提纲，包括项目亮点、角色分工、演示顺序和常见问题 |
| 第二阶段 | 整合最终提交目录，检查文件命名、封面、目录、页码、图号、表号 |

### A.3 具体任务清单

#### 7.6 前

1. 通读《需求规格说明书》全文，重点检查：
   - 是否还有“role 单字段支持多角色”的矛盾说法。
   - 签到方式是否统一为“按钮触发 + 二维码 + 定位校验”。
   - 预约状态、设备状态、报修状态、信用恢复状态是否前后一致。
   - 图名、图号、章节引用是否对应。
   - 是否有明显 AI 腔、重复句、过度理想化表达。
2. 人工润色语言：
   - 把过于机械的句子改成课程设计文档常见表达。
   - 删除空泛形容词，保留可验证要求。
   - 对“高并发”“高可用”等超出课程范围的词进行收敛，写成“课程实现目标”。
3. 整理 7.6 检查版：
   - 确保 Word 能正常打开。
   - 目录能更新。
   - 图片不糊、不跨页断裂严重。
   - 文件名统一为 `230710_8_需求规格说明书.docx`。

#### 7.13 前

1. 根据 C 的设计文档，统一《概要设计说明书》《详细设计说明书》的封面、目录、编号。
2. 检查设计文档是否能追溯到需求编号 FR-01 到 FR-13。
3. 与 B 确认原型截图是否放入设计文档合适位置。
4. 建立一张简短追溯检查表：需求编号、对应模块、对应页面、对应测试点。

#### 7.17 前

1. 整合《项目开发计划书》：
   - 项目背景、目标。
   - 任务分解。
   - 进度安排。
   - 风险管理。
   - 质量保证。
2. 整合《项目开发记录表》：
   - 记录真实发生的需求校对、图表调整、设计讨论、模块实现、测试修复、文档整合。
   - 不编造不存在的工作，但可以按课程文档风格整理活动。
3. 检查最终提交包：
   - 需求规格说明书。
   - 概要设计说明书。
   - 详细设计说明书。
   - 软件设计说明书。
   - 测试计划。
   - 用户手册。
   - 项目开发计划书。
   - 项目开发记录表。
   - 软件成品和源码。
4. 整理答辩用说明：
   - 每位组员负责模块。
   - 三条主要演示路径。

1. 图表：
   - 调整线条，减少交叉。

   - 避免明显“模板感”或过度花哨。

   - 每条演示路径必须能从登录开始走到业务完成。
   - 每个角色至少准备一条完整操作路径。
   - 每个主要异常至少准备一个可说明场景，例如预约冲突、签到失败、设备维修中。

## 五、角色 C Handoff：设计与数据负责人

### C.1 角色定位

角色 C 是“系统设计和数据一致性负责人”。核心目标是把需求转成可实现的软件结构，让 D 能按设计开发，让 A 能按设计写文档，让 B 能按设计调整图。

### C.2 负责范围

| 阶段 | 任务 |
|---|---|
| 第一阶段 | 核对需求规格中的数据库、状态字典、权限模型 |
| 第一阶段 | 给 B 提供 ER 图和表结构图调整意见 |
| 第一阶段 | 为原型提供页面字段和状态枚举 |
| 7.13 前 | 主写《概要设计说明书》《详细设计说明书》 |
| 第二阶段 | 主写或整合《软件设计说明书》 |
| 第二阶段 | 为 D 提供接口、数据表、状态流转和模块边界 |
| 第二阶段 | 审阅 B 的黑盒测试用例，确认关键状态和异常场景没有漏项 |

### C.3 概要设计说明书建议结构

1. 引言。
2. 总体设计。
3. 系统架构。
4. 模块划分。
5. 数据设计。
6. 接口设计。
7. 权限与安全设计。
8. 异常处理与日志设计。
9. 部署与运行环境。

### C.4 详细设计说明书建议结构

1. 引言。
2. 模块详细设计。
3. 数据库表详细设计。
4. 关键业务流程设计。
5. 接口详细设计。
6. 核心算法与规则。
7. 异常处理。
8. 测试关注点。

### C.5 关键设计决策

| 决策 | 说明 |
|---|---|
| 多角色 | 采用 RBAC：user_account、role、user_role、permission、role_permission |
| 管辖范围 | admin_lab_scope 控制实验室管理员可管理的数据范围 |
| 预约冲突 | 以设备编号、开始时间、结束时间、有效状态做冲突检测 |
| 并发预约 | 同资源同时间段加事务锁或唯一约束，保证只成功一条 |
| 签到 | 按钮触发，二维码和定位作为校验因子 |
| IoT | 通过模拟服务和 iot_command_log 记录指令 |
| 信用 | 扣分和恢复都写入 credit_log，不直接覆盖历史 |
| 封禁 | ban_record 独立记录，便于追踪和解除 |
| 通知 | notification 独立记录，业务事件触发 |
| 操作审计 | operation_log 记录关键管理操作 |

| 内容 | 说明 |
|---|---|
| 数据表清单 | 表名、字段、主键、外键、状态枚举 |
| 接口清单 | 登录、预约、审批、签到、报修、信用、通知、统计 |

## 六、角色 D Handoff：软件实现与集成负责人

### D.1 角色定位

角色 D 是“软件成品主实现 + 集成负责人”。为减少代码沟通成本，建议由 D 主导代码整体架构和集成。其他人可以提供原型、文档、测试用例、局部代码建议，但最终合并由 D 控制。D 重点保证系统能跑、核心流程能演示、数据能闭环；测试用例设计、截图和演示脚本由 B/A 分担。

### D.2 技术实现建议

课程设计可以采用轻量但完整的 Web 系统实现。

| 层 | 建议 |
|---|---|
| 前端 | Vue/React/普通 HTML + CSS + JS 均可，重点是可演示 |
| 后端 | Spring Boot/.NET/Node/Python Flask 均可，选组内最熟的 |
| 数据库 | MySQL/SQLite/SQL Server 均可，课程演示可用 SQLite 降低部署成本 |
| 图表 | ECharts 或简单统计卡片 |
| IoT | 模拟接口，写入日志即可 |
| 定位/二维码 | 可用模拟按钮或前端生成假校验结果，但数据结构要保留 |

### D.3 成品功能优先级

#### 必须完成

1. 登录与角色视图。
2. 学生资源查询。
3. 提交预约。
4. 管理员审批预约。
5. 签到签退。
6. 学生和管理员报修。
7. 管理员处理报修和设备状态。
8. 信用扣分和查看信用分。
9. 系统管理员维护基础数据。
10. 基本通知或待办提醒。

#### 应完成

1. 设备可用时段管理。
2. 信用恢复申请与审核。
3. 封禁记录。
4. 操作日志。

### D.4 测试执行负责内容

测试用例表由 B 主写，C 审阅关键状态和数据一致性，D 负责按实际系统执行测试、记录结果并修复问题，A 负责放入正式文档。

| 测试类型 | 测试重点 |
|---|---|
| 功能测试 | 登录、预约、审批、签到、报修、信用、统计 |
| 权限测试 | 学生、实验室管理员、系统管理员访问边界 |
| 数据一致性测试 | 预约冲突、状态流转、扣分日志 |
| 异常测试 | 设备维修、定位失败、二维码失败、IoT 失败 |
| 并发测试 | 同设备同时间段多人预约只成功一条 |
| 界面测试 | 页面跳转、表单校验、状态显示 |

### D.5 用户手册技术配合内容

用户手册由 A 整合文字，B 提供截图和页面路径，D 提供真实运行步骤、默认账号、部署地址和注意事项。

| 用户 | 手册内容 |
|---|---|
| 学生 | 登录、查询资源、提交预约、取消预约、签到签退、报修、查看信用 |
| 实验室管理员 | 审批预约、处理报修、维护设备、修改可用时段、处理违规、审核恢复 |
| 系统管理员 | 用户管理、角色权限、实验室设备管理、参数配置、日志查看 |

### D.6 代码质量要求

1. 删除明显无意义注释，例如“这里是函数”“设置变量”等。
2. 保留必要注释，例如并发预约、信用扣分、状态流转。
3. UI 不要过度模板化，按钮和表格状态要贴合业务。
4. 关键状态使用枚举或常量，不散落字符串。
5. 预约提交、扣分、恢复、封禁要避免重复提交。
6. 所有演示数据要合理，不要出现明显测试垃圾数据。

## 九、风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 图文不一致 | 文档写了新机制，图还是旧机制 | B 统一维护图，A 最终核对 |
| 数据库与代码不一致 | 文档表结构和实际实现不同 | C/D 每次改表要同步说明 |
| 原型与成品差距大 | 老师看到原型和最终系统不像一个项目 | B/D 统一页面结构和命名 |
| 后期文档堆积 | 7.17 前才补文档 | A 提前搭框架，每天填充 |
| 答辩解释困难 | 图、代码、文档口径不统一 | 每人准备自己负责模块的 2 分钟说明 |
| 重复改图 | 同一图出现多个版本 | 所有图只认 `图/` 文件夹最新版 |
