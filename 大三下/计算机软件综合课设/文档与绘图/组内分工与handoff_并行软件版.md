# 智能实验室预约与设备管理系统组内分工与 Handoff（并行软件版）

> 本文档依据最新版《230710_8_需求规格说明书》的 M1～M8 模块、FR-01～FR-13 功能需求重新分工。  
> 核心目标：四位成员都参与软件实现，每人负责一个可运行、可测试、可解释的业务模块；角色 A 额外承担公共基础和最终集成，但不替其他成员补完其模块。  
> 本版本替代“一个人写全部软件、其他人主要写文档或画图”的旧思路。旧 Handoff 文件保留，仅用于对照，不再作为实际认领依据。

## 一、分工目标与基本原则

### 1. 分工目标

1. 四个人都必须提交实际软件代码，不设置纯文档、纯画图或纯测试角色。
2. 每个人负责一个纵向业务切片，工作范围同时包含：
   - 页面或交互入口。
   - 后端接口和业务逻辑。
   - 本模块拥有的数据表或数据访问。
   - 权限与异常处理。
   - 可运行检查或测试。
   - 本模块对应的设计、测试和用户手册内容。
3. 各模块可并行开发，但必须共用同一套账号、状态、数据库和接口约定。
4. A 的业务模块相对较小，以补偿其公共基础、合并、部署和最终集成工作。
5. 每个人都能在答辩中独立演示和解释自己的软件模块。

### 2. 架构原则

1. 使用一个仓库、一个后端、一个前端、一个数据库的模块化单体。
2. 不拆微服务，不引入消息队列，不为课程项目增加分布式部署。
3. “负责接口”指负责模块内的路由、服务、数据和测试，不是各自创建一套独立系统。
4. 技术栈由全组在开发开始前一次确定，之后不随意更换。
5. 已有依赖能完成的功能不再新增同类依赖；课程演示能用简单实现解决的，不做复杂平台化封装。

### 3. 当前首版技术基准（2026-07-01 新增）

> **【本次新增】** B 模块是首个可运行模块。以下约定以其已通过测试的实现为基准，供 A/C/D 继续开发；变更时必须同步修改代码、需求规格说明书和本 Handoff。

| 项目 | 当前统一暂定基准 |
|---|---|
| 部署形态 | 单服务器上的模块化单体 Web 系统；浏览器在线访问，后端和数据库均在服务器端，客户端不得直连数据库 |
| 编程语言 | Python 3.12+；开发机当前 3.13.0，线上服务器 3.12.3 |
| Web 框架 | Flask 3.1.3；全组共用一个 Flask 应用 |
| 数据库 | SQLite 3.45+（Python `sqlite3`）；线上服务器 3.45.1，开发机当前 3.53.0；全组共用一个服务器数据库文件 |
| 线上部署 | `http://example.com`；Nginx → Gunicorn → Flask，应用服务为 `lab-system.service` |
| SQLite 类型 | 实际建表统一用 `INTEGER`、`REAL`、`TEXT`、`BLOB`；需求旧表中的 `bigint`→`INTEGER`，`varchar/text/datetime`→`TEXT` |
| 开发环境 | conda `csv` 环境；依赖统一写入 `requirements.txt` |
| 字符与数据 | 源码、数据库文本和 HTTP JSON 统一使用 UTF-8 |
| 时间 | 服务器设为 Asia/Shanghai；使用 `YYYY-MM-DDTHH:MM:SS`，精确到秒，当前版本不接收带时区偏移的时间 |
| 数据库初始化 | 各模块提交 `schema.sql` 或由 A 合并到统一初始化入口；不得只修改个人本地数据库 |
| 缓存/异步 | 首版不引入 Redis、消息队列和微服务 |

统一实现边界：

1. 数据库路径必须通过配置传入，源码不得出现个人绝对路径。
2. 浏览器只能提交业务字段；登录身份、预约资格、资源状态和管理员管辖范围必须由服务端取得。
3. 创建预约使用 `Idempotency-Key` 请求头，对应 `reservation.request_id` 唯一字段。
4. 时间段按半开区间 `[start_time, end_time)` 处理；首尾相接允许预约，真正重叠才冲突。
5. SQLite 写业务使用短事务；预约创建通过 `BEGIN IMMEDIATE` 保证冲突检查与写入不可被并发穿透。
6. 若全组在共享表冻结前改用 MySQL/PostgreSQL，只替换数据库连接和锁实现，不改变字段语义、状态或测试标准。

### 4. 反重复劳动原则

1. 软件实际页面同时作为原型、设计截图和用户手册截图来源，默认不再单独制作一套不可复用原型。
2. 已有需求图能表达清楚时不重画；必须修改的图由对应模块负责人修改。
3. 每个模块原则上只维护一张核心流程图，除非老师明确要求更多图。
4. 每个人写自己模块的文档正文，A 只负责整合格式、目录和最终提交，不替其他人补正文。
5. 同一状态、字段、接口只保留一个权威定义，不在不同文档中复制出多个版本。

### 阶段 0：公共约定冻结（6.30～7.1）

全员共同完成，任何成员不得缺席：

1. 确定前端、后端和数据库技术栈。
2. 确定本地启动方式和最低运行环境。
3. 确定目录结构、代码格式和分支规则。
4. 确定统一状态枚举：预约、设备、报修、违规、信用恢复、封禁。
5. 确定统一账号、角色、权限和管辖范围模型。

8. 将以上结论记录到本文件或单独的公共约定文件中。

### 阶段 1：并行开发（7.2～7.10）

1. A 先提供可运行公共骨架，各成员基于同一骨架开发。
2. 每个人优先完成本模块最短正常流程，再补异常和增强功能。
3. 每天至少向主分支合并一次可运行的小改动。
4. 模块依赖未完成时使用统一演示数据或最小桩函数，不另外复制对方模块。
5. 任何数据表、状态或接口变更必须先通知受影响成员。

### 阶段 2：端到端集成（7.11～7.13）

重点打通三条主路径：

1. 预约使用路径：登录 → 查询资源 → 提交预约 → 管理员审批 → 签到 → 签退 → 通知。
2. 设备维修路径：设备报修 → 管理员确认 → 设备维修 → 受影响预约处理 → 恢复设备 → 通知。
3. 信用管理路径：疑似违规 → 管理员确认 → 扣分 → 封禁或恢复 → 通知 → 统计展示。

### 阶段 3：测试、文档和交付（7.14～7.17）

1. 每个人完成自己模块的功能、权限、异常和数据一致性测试。
2. 每个人提供自己模块的真实系统截图和用户操作步骤。
3. 每个人完成自己模块在概要设计、详细设计和测试报告中的内容。
4. A 合并文档格式和提交包，其他成员必须审核自己提供的内容。
5. 全员完成一次从空数据库到系统启动、登录和三条主路径演示的彩排。

5. 演示数据脚本由 A 提供统一入口，各模块负责人提供自己模块的数据片段。

| 统计查询 | `GET /api/statistics` | 管理员 |

### 5. 统一返回和错误处理

以 B 首版已实现的格式作为当前基准，不创建多套包装器：

```json
{
  "reservation": {}
}
```

列表使用 `{"reservations": []}`；失败使用 `{"error": "错误说明"}`。创建成功返回 201，普通查询和状态操作成功返回 200；参数错误返回 400，权限不足返回 403，业务冲突或非法状态返回 409，尚未接入必要模块返回 503。

错误至少区分：

- 未登录。
- 无角色或功能权限。
- 超出实验室管辖范围。
- 参数或表单校验失败。
- 状态不允许当前操作。
- 预约时间冲突。
- 重复提交。
- 数据不存在。
- 系统内部错误。

## 六、角色 A Handoff：平台与集成负责人

### A.1 角色定位

A 负责所有模块共用的最小平台能力，并保证最终系统可以从空环境启动、初始化、登录、运行和打包。A 是集成负责人，不是其他模块的代写人。

### A.2 软件负责范围

1. 项目仓库和基础目录。
2. 本地配置模板和启动说明。
3. 数据库连接、统一迁移和演示数据入口。
4. 登录、退出、当前用户查询。
5. 多角色用户的当前角色切换。
6. RBAC 权限校验。
7. 实验室管理员管辖范围校验。
8. 用户、角色、权限基础管理页面和接口。
9. 系统参数查看、修改和版本记录。
10. 公共操作日志记录函数和日志查询页面的基础能力。
11. 统一错误返回和必要的全局异常处理。
12. 最终代码合并、启动脚本、部署说明和发布检查。

### A.3 页面范围

- 登录页。
- 角色切换入口。
- 用户管理页。
- 角色与权限管理页。
- 管辖范围管理页。
- 系统参数页。
- 操作日志查询页。

### A.4 测试重点

1. 正确和错误账号登录。
2. 一个用户拥有多个角色并成功切换。
3. 学生不能访问管理员接口。
4. 实验室管理员不能访问非管辖实验室数据。
5. 系统管理员参数修改生效并留下版本记录。
6. 关键操作生成操作日志。
7. 从全新数据库执行初始化后可以登录。

### A.5 阶段任务

#### 7.3 前

- 建立项目骨架和仓库规则。
- 提供数据库初始化入口。
- 完成登录最小链路和公共返回格式。
- 提供统一演示账号。

#### 7.10 前

- 完成 RBAC、角色切换、管辖范围和系统参数。
- 向 B/C/D 提供稳定的权限和参数调用方式。
- 完成基础用户管理。

#### 7.13 前

- 合并四个模块，处理公共配置和迁移冲突。

5. B 调用 D 创建管理员待审批通知。
6. B 调用 A 记录关键操作日志。

### 2. 预约审批

1. B 调用 A 校验管理员管辖范围。
2. B 再次读取 C 的设备状态并检查预约冲突。
3. B 更新预约状态。
4. B 调用 D 通知学生审批结果。
5. B 调用 A 记录审批日志。

### 3. 签到签退

1. C 从 B 查询预约和当前状态。
2. C 从 A 读取签到时间窗口参数。
3. C 完成按钮、二维码和定位的课程级校验。
4. C 写入签到记录并调用 B 更新预约状态。
5. C 写入 IoT 模拟日志。
6. 异常情况由 C 调用 D 创建疑似违规或通知。

### 4. 报修维修

1. C 校验报修人和设备权限。
2. C 创建报修记录并冻结设备预约能力。
3. C 调用 D 通知管理员。
4. 管理员确认维修后，C 查询并调用 B 处理受影响预约。
5. B 更新预约后调用 D 通知学生。
6. 维修完成后 C 恢复设备状态。

### 5. 违规扣分和封禁

1. D 根据 B 的预约和 C 的签到/报修记录创建疑似违规。
2. 管理员通过 A 的权限和管辖范围校验后确认违规。
3. D 在一个事务中写入违规状态和信用日志。
4. D 根据 A 的参数判断是否创建封禁记录。
5. D 创建信用变化或封禁通知。
6. B 在后续预约提交前查询 D 的有效封禁。

## 十一、Git 与代码协作规则

### 1. 仓库规则

1. 只使用一个代码仓库。
2. `main` 始终保持可启动；如使用 `develop`，也只保留这一条共享开发分支。
3. 每个任务使用短分支，例如：
   - `feature/a-rbac`
   - `feature/b-reservation-conflict`
   - `feature/c-repair-flow`
   - `feature/d-credit-ban`
4. 分支持续时间尽量不超过两天，避免最后集中合并。
5. 提交信息说明“做了什么”，不要使用“update”“修改一下”等无法追踪的描述。

### 2. 合并规则

1. 提交合并前必须能启动，不能把明显无法运行的代码交给 A 修复。
2. 提交时写明：功能、迁移、接口、测试方法和已知问题。
3. 修改共享表、共享状态或公共接口时，至少由 A 和一名受影响模块负责人审阅。
4. 合并冲突由代码作者与 A 一起解决，不由 A 单方面猜测业务逻辑。
5. 每天结束前所有成员同步当前可合并状态。

### 3. 禁止事项

- 禁止四个人分别创建独立前后端项目后再尝试拼接。
- 禁止直接修改他人拥有的数据表而不通知。
- 禁止复制一份接口实现到自己模块规避等待。
- 禁止只提交截图、不提交可运行代码。
- 禁止页面完成但接口、权限和异常完全空缺时宣称模块完成。
- 禁止最后一天集中提交大量未联调代码。

## 十二、测试与交叉审查

### 1. 每人最低测试责任

每个角色至少留下：

1. 一条正常主流程检查。
2. 一条权限或管辖范围检查。
3. 一条非法状态或参数检查。
4. 一条重复提交或幂等检查；不适用时换成模块关键异常。
5. 一份可重复执行的测试步骤或自动测试。

### 2. 交叉审查安排

| 审查者 | 重点审查模块 | 重点问题 |
|---|---|---|
| A | B | 权限、参数、初始化和接口一致性 |
| B | C | 设备状态、可用时段和预约联动 |
| C | D | 签到/报修数据是否正确驱动违规和统计 |
| D | A | 角色、封禁和权限是否正确限制操作 |

### 3. 最终三条验收路径

每条路径都必须从登录开始，使用最终系统真实页面，不使用单独原型替代：

1. 学生预约并完成使用。
2. 学生或管理员报修并完成维修处理。
3. 管理员确认违规并完成扣分、封禁或恢复。

## 十三、文档、图表和答辩责任

### 1. 每个人负责自己的文字

每位成员应提供：

- 模块目标和范围。
- 数据表和状态说明。

### 2. 图表规则

## 十五、风险与处理方式

| 风险 | 典型表现 | 处理方式 |
|---|---|---|
| 公共约定未冻结 | 四人使用不同状态和字段 | 7.1 前冻结最小约定，后续通过变更模板修改 |
| A 变成唯一救火者 | 其他模块无法运行，全部交给 A 修复 | 模块负责人必须先保证自己的分支可启动并提供测试步骤 |
| 长分支难以合并 | 一周后一次性提交大量代码 | 分支不超过两天，每天合并小改动 |
| 重复实现 | 各模块各写一套用户、通知或设备查询 | 公共能力按本文件归属，只保留一个实现 |
| 数据库冲突 | 多人直接改同一张表 | 表有明确负责人，修改使用迁移脚本并提前通知 |
| 原型与成品重复 | B 做完原型后又重新实现前端 | 直接使用实际页面作为原型，除非老师明确要求独立原型 |
| 图表工作挤占编码 | 花大量时间调整线条和截图 | 每人最多一张核心图，已有图优先复用 |
| 功能过多无法按期完成 | 二维码、定位、IoT、统计过度实现 | 使用课程级模拟和简单查询，先确保三条主路径 |
| 文档最后堆积 | 软件完成后无人能说明设计 | 每个模块完成一个功能时同步补一段设计和测试记录 |
| 权限遗漏 | 页面隐藏但接口可越权 | 所有权限在后端校验，前端隐藏不作为安全措施 |
| 重复扣分或重复预约 | 重复点击生成多条业务记录 | 关键操作保留幂等检查和事务边界 |
